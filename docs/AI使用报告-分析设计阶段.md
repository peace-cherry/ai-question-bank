本报告记录小组在需求分析与系统设计（OOA/OOD）阶段使用 AI 工具辅助开发的实际情况，覆盖工具选型、上下文与提示词设计、人机协作过程与人工评审、结果分析、问题反思与总结。原始会话历史导出、代码 diff、评审记录等可作为附件另行提交。

## 一、概述

### 1.1 工具与Agent简介

| 项 | 内容 |
|----|------|
| 工具/Agent | 对话式 AI 助手＋编码 Agent（含代码生成、AI 自查、测试用例与文档起草） |
| 类型 | 对话式助手 · 编码 Agent · 自动化验证（GitHub Actions CI） |
| 核心功能 | 需求/接口契约解读、C11 后端与纯前端代码生成、Prompt 模板约束、AI 自查、文档结构化 |
| 已知局限 | 输出可能"看起来对但编译不过"；可能调用不存在的函数/库；可能建议硬编码密钥；无法在 Windows 本地编译验证 |
| 团队工作流中的角色 | 承担 80% 以上初始代码/文档生成，人聚焦架构与安全评审，CI 作为客观质量闸门 |

### 1.2 任务场景

- **所属阶段**：需求分析（选题/计划/需求/技术选型/UI 原型）→ 系统设计（OOA/OOD、架构、数据、接口契约）。
- **任务目标**：产出需求/计划/时间轴/架构/接口等分析与设计文档，并据此驱动 C11 后端（libmicrohttpd＋SQLite3）、纯静态前端与内置 Pi 解题服务（Node/TS，Pi 0.84.1）的实现。
- **验收标准**：文档与实现一致；`gcc -std=c11 -Wall -Wextra` 零警告；CI（build＋test）全绿；PR 至少 1 人 Approve；安全红线（API Key 不出后端、`.env` 不入库等）不触碰。
- **交/不交给 Agent 的理由**：C 技术栈学习曲线陡、接口与规范重复性高，适合 AI 降本增效；技术选型拍板、安全边界与多租户口径等由人工决策。

## 二、上下文与提示设计

### 2.1 上下文准备

- **提供内容（"最小充分集"）**：`docs/AGENT.md`（项目唯一权威手册）、`CONTRIBUTING.md`、根/模块 `Makefile`、`server/include/*.h` 头文件、1~2 份相关源码、模块接口文档（`auth.md`/`questions.md`/`kvstore.md`/`pi-chat-api.md`/`teacher-api.md`/`ai-access.md`）；设计类任务额外喂入 `docs/architecture.md`、`docs/kvstore.md` 与功能说明书。
- **裁剪策略**：只喂与任务相关的充分集——给太多 AI 会迷失、给太少不合规范；刻意不提供 `.env` 与真实密钥，敏感信息只进 `.env.example` 占位符。
- **维护与更新**：`AGENT.md`、架构与接口文档由戴儒骋、卢恒毅统一维护，随项目结构/构建命令/编码规范变更同步更新。

### 2.2 提示词设计

- **关键提示词**：任务前粘贴固定约束块——"你是本项目的 C 技术栈开发者……输出必须满足：C11 零警告、HTTP 错误 JSON、内存安全（kv_* 释放）、禁止硬编码密钥、签名与头文件一致、不破坏现有功能、给出补充测试用例"；文档类用"Markdown 风格与现有 docs/ 一致、相对路径、事实以 AGENT.md 与功能说明书为准，不编造"模板。
- **迭代过程**：初版仅要求"生成代码"→ 发现编译不过/风格漂移/硬编码风险 → 逐版补入「零警告＋LDLIBS 核对＋kv_* 释放＋密钥走环境变量＋不破坏 `/api/v1/health`」等硬约束；文档模板补入「事实不编造」。
- **原始记录**：完整会话历史、日志或截图作为附件提交。

## 三、使用过程与人工评审

### 3.1 协作过程

按时间线描述「任务分解 → Agent 执行 → 人工检查 → 反馈修正」迭代（依据上游主线 Squash-merge 提交记录）：

| 时间 | 任务 | 人机协作 |
|------|------|----------|
| 09-27 | 框架与技术选型 | AI 辅助技术栈改造（改 C＋libmicrohttpd＋SQLite＋cJSON）与 CI 修复；人定选型 |
| 09-29~10-13 | 用户认证 | AI 生成 auth 接口；人审安全与 session 清理；注册＋users 迁移 kv_store |
| 10-12~10-20 | 存储层 | AI 生成 kv_store 目录式存储层与 18 断言单元测试；人审所有权与命名 |
| 10-05~10-30 | 题库 | 只读 API → 写接口 CRUD（PR #15）；AI 生成，人审多租户隔离 |
| 10-22~11-05 | AI 解答 | 独立 Node/TS Pi 服务异步解题＋AI 授权＋教师 API 配额（PR #14/#16/#17）；人审安全边界 |
| 10-20~11-08 | 前端 | 登录/注册/题库/对话页、加载态与竞态修复（PR #12/#19/#20/#21）；AI 生成，人走查 |
| 10-07~11-09 | 文档 | 需求/计划/时间轴/架构/接口/本报告；AI 起草，人核事实 |

耗时结构（定性）：上下文准备与提示词编写占比高，Agent 生成快，人工评审与返工是主要隐形成本。

### 3.2 人工评审

- **评审人与方式**：卢恒毅（安全/架构/测试）＋各模块 code owner；代码 Review、文档评审、测试验证（CI＋本地/服务器演示）。
- **采纳情况**：以直接采纳为主，部分"修改后采纳"（如 AGENT.md 冲突取上游版、文档口径修正、接口字段对齐）；对不合规输出整体拒绝（硬编码密钥、明文密码一律打回）。量化采纳率/返工率待以附件统计为准。
- **规范执行**：代码合并前必须履行 PR Review——≥1 人 Approve＋CI 全绿＋作者不合并自己的 PR（Squash merge）。

## 四、结果分析

### 4.1 产出质量评估

- **正确性**：`make build` 零警告＋`make test`（auth/health/questions/kv/ai_access/chat/teacher_api 七组）通过，CI 全绿方可合并。
- **一致性**：接口契约先行（`auth.md`/`questions.md`/`pi-chat-api.md`/`teacher-api.md`/`ai-access.md`＋OpenAPI），实现与文档逐接口核对；发现并修正旧 `kv_` 前缀与现实现"同名表"漂移。
- **可维护性**：C11 snake_case 命名、模块分层（routes→services→db→kv_store→ai_client）、`AGENT.md` 编码规范约束。
- **安全性**：API Key 不出后端（教师 Key 加密托管、主密钥独立注入）、`.env` 不入库、路径穿越防护、参数化 SQL、无硬编码密钥；AI 授权默认拒绝。

### 4.2 效率与成本分析

- **效率（预估口径，来自 `docs/AI辅助开发计划.md`）**：

| 场景 | 无 AI（预估） | 有 AI（预估） | 提升（预估） |
|------|----------------|----------------|----------------|
| 新接口开发（C 后端） | 4–6 小时 | 1–2 小时 | 60–70% |
| 前端页面开发 | 3–4 小时 | 0.5–1 小时 | 70–80% |
| 冒烟测试编写 | 1–2 小时 | 15–30 分钟 | ~75% |
| Bug 修复 | 1–2 小时 | 20–40 分钟 | ~60% |
| 文档编写 | 2–3 小时 | 30–60 分钟 | ~70% |

- **直接成本**：Token/Credits 消耗（尚未精确统计，待补）。
- **隐形成本**：上下文准备、提示词迭代、人工评审与返工耗时显著；Windows 无法本地编译导致"以 CI 结果为准"的往返等待。
- **结论**：扣除隐形成本后，C 技术栈下新接口/文档产出仍有实质提速，但安全评审与契约核对不可省略。已观察到的实际成效：AI 辅助完成 kv_store（PR #5，18 断言）、题目只读 API（5 道 seed）、前端三页（35 项端到端断言）首轮闭环，并支撑 CRUD、Pi 异步解题、教师 API 配额快速低漂移落地。

## 五、问题与反思

### 5.1 技术问题

| 问题 | 解决措施 |
|------|----------|
| AI 代码"看起来对但编译不过" | 以 CI `make build` 结果为准，红了按日志（精确到文件与行号）修 |
| 声称不依赖某库但实际需要 | 核对 `server/Makefile` LDLIBS |
| 生成 Windows-only / 不存在的函数 | 对照 `server/include/*.h`，C11 跨平台由 CI 暴露 |
| Windows 本地无法编译 C | 以 GitHub Actions CI 为准；可选 WSL2 |
| 文档与实现漂移（旧 `kv_` 前缀、过期接口） | 接口/文档负责人逐接口核对后合入，回写 `AGENT.md` 常见坑 |

### 5.2 流程与协作问题

- 评审环节曾出现文档/接口漂移，需坚持「契约先行＋逐接口核对」。
- 上下文文档（AGENT.md）更新滞后会导致 Agent"理解过期"，需随结构变更及时更新。
- 早期提示词约束不全，已沉淀为固定约束块提高复用性。
- 避免过度依赖：不看 AI"说没问题"就合入，坚持以 CI 与人工评审为闸门。
- 改进建议：建立 OOA/OOD 图到接口契约的一致性检查；文档生成做"引用路径自检＋事实来源标注"，减少文档间重复与冲突。

### 5.3 规范与诚信问题

- **数据与代码安全**：未将 `.env`、密钥或他人代码提交给 AI；敏感信息只进 `.env.example` 占位符。
- **开源许可合规**：cJSON 为 MIT 单文件库、随仓库分发；Pi 依赖固定版本（0.84.1）。
- **学术诚信**：AI 生成部分按课程要求标注与声明，保留会话历史与评审记录作为附件备查。

## 六、总结与心得

- **效果与价值**：AI 在"需求解读、接口契约、文档结构化、重复性代码"上效率显著，是 C 技术栈下高质量快速开发的关键杠杆。
- **能力边界认识**：AI 擅长"给定规范后的生成与自查"，不擅长"拍板技术选型、安全边界、多租户口径"；复杂设计仍需人主导。
- **下一阶段调整**：以 OOA/OOD 契约驱动 F03（试卷）、F04（审核）、F06（分支树）等 P0 功能；每次任务固定走"喂对文件 → 约束到位 → AI 自查 → CI 兜底 → 人工审安全"闭环；第三阶段输出《AI 使用说明（开发阶段）》，第四阶段输出《AI 辅助测试分析报告》。
