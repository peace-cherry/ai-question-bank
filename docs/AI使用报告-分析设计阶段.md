## 一、报告概述

本报告说明 AI+题库智能教学平台在**分析设计阶段**如何系统化使用 AI 辅助完成需求分析与系统设计，并说明产出物的质量核验方式。

**团队 AI 协作的总体方法**（来自 `docs/AI辅助开发计划.md`）：

> **喂对文件 → 约束到位 → AI 自查 → CI 兜底 → 人工审安全**

对应工作流：需求理解 → 喂给 AI → 生成代码/文档 → AI 自查 → 本地 review → CI 验证 → PR Review → 合并。

## 二、分析设计阶段的 AI 使用方式

### 2.1 三阶段分工

| 阶段 | AI 做什么 | 人做什么 |
|------|----------|----------|
| 需求理解 | 解读功能说明书、接口契约（`docs/api.md` 及模块文档），输出结构化需求与用况 | 确认需求正确性、定业务口径 |
| 系统设计 | 依据 `AGENT.md`＋头文件＋`Makefile`，产出架构分层、数据模型、接口签名、OOA/OOD 图 | 评审架构约束与安全红线、拍板技术选型 |
| 文档生成 | 按文档 Prompt 模板起草 Markdown | 核对事实、统一口径、合并进主分支 |

### 2.2 喂给 AI 的「最小充分集」

所有 AI 任务均先投喂 `docs/AGENT.md`（项目唯一权威手册）＋ `CONTRIBUTING.md`＋根/模块 `Makefile`＋1~2 份相关现有源码或文档，并附固定 Prompt 约束块（见 `docs/AI辅助开发计划.md` §3）。设计类任务额外喂入：`docs/architecture.md`、`docs/kvstore.md`、`server/include/*.h`、模块接口文档。

### 2.3 文档生成 Prompt 模板（设计阶段沿用）

```
你是本项目的文档维护者。项目背景见附带的 AGENT.md 与功能说明书。
请完成：<具体任务>
输出必须满足：
1. Markdown 格式，与现有 docs/ 风格一致；
2. 引用的文件路径使用相对路径（如 docs/architecture.md）；
3. 事实信息以 AGENT.md 和功能说明书为准，不编造。
```

## 四、设计阶段（OOA/OOD + 架构/接口/数据）的 AI 使用明细

### 4.1 总体架构设计

AI 依据约束生成分层架构（见 `docs/architecture.md`）：

```
web（静态页） ──HTTP/JSON /api/v1/*──▶ server（C11: libmicrohttpd+SQLite3+libcurl）
                                        └─ 内部 HTTP ─▶ ai-service（Node/TS + Pi 0.84.1）──▶ 大模型
```

- **分层**：路由层（routes）→ 业务层（services）→ 数据层（db）→ 存储层（kv_store）→ AI 层（ai_client/ai-service）。
- 人评审锁定安全红线：API Key 永不出后端、`.env` 不入库、路径穿越防护、多租户隔离、无硬编码密钥、参数化 SQL。
- 后续演进（已落地）：教师 API v1.3 模式（`AI_ROUTING_MODE=teacher`，Key 加密托管、按日额度）。

### 4.2 数据设计

- AI 输出初始「关系表」方案，经评审演进为**双轨存储**：关系数据走 `db.c`；目录式/弱 schema 数据走 `kv_store`（namespace → SQLite 同名表）。
- 关键迁移：users/questions 已迁入 kv_store（PR #5/#10/#13），AI 授权/审计为专用关系表；接口与所有权约定固化在 `docs/kvstore.md`。
- 人工核验：`kv_*` 返回值释放（`char*`→`free`、`char**`→`kv_free_str_array`）、namespace 命名合法性。

### 4.3 接口 / 契约设计（设计先行）

AI 按 Headers/路由约定产出接口契约，作为「先文档后代码」的单一事实来源：

| 契约文档 | 覆盖 |
|----------|------|
| `docs/auth.md` | 登录/注册/登出/`me`、Bearer Token、状态码 |
| `docs/questions.md` | 题目只读/CRUD、kv_store `qdata` 字段、数据初始化 |
| `docs/pi-chat-api.md`＋`pi-chat-openapi.json` | chat 提交(202)/查询/取消、1.2/1.3 契约 |
| `docs/teacher-api.md` | 教师 API 配置 GET/PUT/PATCH、脱敏 |
| `docs/ai-access.md` | AI 授权查询、审计、默认拒绝 |

### 4.4 OOA/OOD 图表（第二阶段交付物，进行中）

按 `docs/项目开发时间轴.md` Sprint 3 计划，AI 辅助产出面向「题库管理 + AI 解答」的 OOA/OOD：

- 用况图（含：学生提交题目/获取 AI 解答/追问；教师管理题库/试卷/AI 配置；管理员授权/审计）
- 类图 / 包图（分层与模块归属：`routes`/`db`/`kv_store`/`ai_client`/`ai-service`）
- 顺序图（C → Pi 的提交/查询任务序列；学生→教师配额核验）
- 状态图（异步任务：queued → running → done/failed；1 小时过期、取消不提交历史）

> 状态：初稿进行中，作为第二阶段课堂报告（2026-11-12）内容，最终版 2026-11-19 前提交。

### 4.5 设计 → 实现的 AI 闭环

设计一旦成为契约文档，即反向约束 AI 生成代码：**契约先行 → AI 按契约生成 → 自查 → CI（编译+回归）→ PR 人工审查**。实现抓取到的偏离点包括：文档中旧 `kv_` 前缀与现实现「同名表」不符、`make test` 端口冲突、Windows 无法编译等，均已回写进 `AGENT.md` 第 10 章常见坑与 `architecture.md`。

## 五、AI 产出的质量核验

| 层级 | 方式 | 门槛 |
|------|------|------|
| ① 自动（CI） | GitHub Actions：`make build`（`-std=c11 -Wall -Wextra` 零警告）＋`make test`（run_tests.sh 自动发现 auth/health/questions/kv/ai_access/chat/teacher_api 测试组） | CI 全绿方可合并 |
| ② AI 自查 | 逐条回答 `docs/AI辅助开发计划.md` §5.2 的 9 项清单（编译/内存/错误码/密钥/登记/路由/kv 释放等） | 自查通过 |
| ③ 人工审查 | 卢恒毅（安全/架构）＋模块 code owner 对照 `AGENT.md` §5–6 审查，重点缓冲区/指针生命周期/资源释放/多租户 | ≥1 人 Approve |
| ④ 质量数据集 | Pi 解题质量用 `ai-service/eval/fixtures.json` 的 30 个案例验收 | 通过 |

**关键原则**：AI「说没问题」不算数，以 **CI 红绿**为准；文档类输出须与实现逐接口核对后合入。

## 八、经验、风险与改进

**有效经验：**

1. **最小充分集投喂**：给 AI「AGENT.md + Makefile + 头文件 + 1~2 份相关源码」，给太多会迷失、太少会不合规范。
2. **契约/设计先行**：先落接口文档再写代码，AI 生成码与人工实现都以契约为准，显著减少前后端与模块漂移。
3. **CI 兜底**：Windows 无法本地编译 C，所有结论以 GitHub Actions 红绿为准，PR 红了就按日志（精确到文件与行号）修。
4. **AI 自查 + 人工审安全分离**：AI 负责合规性自查，人聚焦架构与安全红线（缓冲区/指针/密钥/多租户）。

**风险与应对：**

| 风险 | 应对 |
|------|------|
| AI 代码「看起来对但编译不过」 | 以 CI `make build` 结果为准 |
| AI 声称不依赖某库但实际需要 | 核对 `server/Makefile` LDLIBS |
| AI 生成 Windows-only / 不存在的函数 | C11 跨平台，对照头文件与 CI 暴露 |
| 文档与实现漂移（如旧 `kv_` 前缀、过期接口） | 文档/接口负责人逐接口核对后合入 |
| AI 建议写死密钥/明文密码 | 红线：AI 产出也拒绝，一律环境变量＋哈希 |

**改进方向：**

- 建立 OOA/OOD 图表到接口契约的一致性检查；将第二/三阶段 AI 使用说明与测试分析形成闭环报告。
- 对 AI 生成文档建立「引用路径自检 + 事实来源标注」，减少文档间重复与冲突。
